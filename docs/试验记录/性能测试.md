# 性能测试：配置耗时速查

> **用途**：不跑测试，快速估一个“调酒”配置在 9×9 / 30×16 / 30×30 上每次猜测大概多少毫秒（ms，1 秒 = 1000 ms）。
> **你的配置**：Anytime 2000 + Templates 100/15 + 暴力 10k ≈ **25–26 ms/次**（30×16），约 **38–40 次/秒**；9×9 ≈ 7.5 ms，30×30 ≈ 51 ms。区间来自暴力线程数：单线程约 26 ms，5 线程约 25 ms。
> **口径**：服务器 Intel Xeon Platinum、8 逻辑 CPU、GCC 12.3 `-O3`，代码 `7871ded`；普通算法单线程（暴力线程数另注）；时间为**根概率已算好之后**的推荐计算，不含根概率本身。
> **一句话**：先查基础算法，再把模板前缀、LTR 上限按毫秒差叠上去；暴力是“替换”而不是“追加”。不要把百分比或倍数连乘。

## 0. 先给结论：你点的这套大概多少

配置：`Anytime 2000` + `Templates` + `prefix 100` + `LTR 15` + `暴力 10000`（最佳招），30×16/99。下面默认按单线程暴力估；UI 默认的 5 线程见本节末尾。

| 项目 | 估算 | 说明 |
| --- | ---: | --- |
| Anytime 2000 基础 | 25.0 ms | 1280 与 2048 之间线性插值；公式给 24.9 |
| Templates 100/15 | +0 | 与基准表同口径 |
| 暴力 10k | +1.1 ms | 单线程；5 线程约 −0.2 ms，见 §7 |
| **合计** | **≈26 ms/次** | 单线程；5 线程约 25 ms（约 40 次/秒） |

同配置换棋盘：

| 棋盘 | 平均每次猜测 | 估算吞吐量 | 备注 |
| --- | ---: | ---: | --- |
| 9×9 / 10 | ≈7.5 ms | ≈133 次/秒 | 暴力 10k 基本无影响 |
| 30×16 / 99 | ≈25–26 ms | ≈38–40 次/秒 | 单线程约 26，5 线程约 25 |
| 30×30 / 225 | ≈51 ms | ≈19–20 次/秒 | 暴力 10k 约 +0.5 ms（单线程） |

> **暴力线程数**：上表的 26 ms 按单线程暴力算。UI 默认是 5 线程；30×16 的暴力残局均值从 16.08 降到 7.92 ms，暴力项约 −0.2 ms，总计约 25 ms，长尾最慢从 4.27 秒降到 1.65 秒。2 线程约 25.3 ms / 2.55 秒。

这些是**平均值**。长尾会差很多：Anytime 1024 在 30×16 的 P99 已经是 67 ms、最大 221 ms；Anytime 2000 通常会更高。暴力 10k 还会把残局最长拖到几秒（§7）。做交互式工具时，别只看平均值。

> 注意：以上不含根概率。真实端到端 = 这些数 + 根概率；根概率本文没有系统测，不能从现有表里推。如果你说的“吞吐量”是整局/秒，还要乘每局猜测次数；本文只测每次猜测。

**不知道从哪开始时**：先用 JavaE + prefix 100 + LTR 15 + 暴力 1000，30×16 约 9.03 ms；想更快就分别试 prefix 50（−3.62 ms）和 LTR 10（−1.22 ms），再结合胜率决定。这是原文的推荐起点；你的 Anytime 2000 配置相当于把基础算法换成 Anytime 2000，再把暴力阈值加到 10000（§4、§7）。

## 1. 五步估法

1. **选棋盘列**：9×9 / 30×16 / 30×30。
2. **查基础算法**：JavaE 直接查表；Anytime N 用表或公式；LowRisk 只有选格。
3. **加模板前缀差**：以 prefix 100 为 0，查 §5 的毫秒差。只改 prefix 时用。
4. **加 LTR 事件差**：以 eventLimit 15 为 0，查 §6 的毫秒差。只改 eventLimit 时用；**别调太大，内部容斥树可能指数爆炸**（§6）。
5. **加暴力修正**：按 §7 的触发率和残局耗时估，不是固定加一个数。

写成一行就是：

```text
t ≈ 基础算法（JavaE / Anytime N）
  + 模板前缀差（相对 prefix 100）
  + LTR 事件差（相对 eventLimit 15）
  + 暴力修正（替换，不是追加）
```

**能直接相加的前提**：各项是在同一基准、同一棋盘上测的**毫秒差**。原文的“1.9 倍”“省 40%”“省 14%”分母不同，不能连乘，也不能把百分比直接相加。详见 §2。

**置信度**：

- **高**：只改 Anytime 节点预算；只改 LTR 上限（prefix 100）；只改暴力阈值（JavaE）。
- **中**：只改 prefix（JavaE）；Anytime + 暴力 10k。
- **低**：Anytime + prefix ≠ 100；同时改 prefix 和 LTR；Anytime + 暴力 10k + 多线程/全部候选。低置信度项要留 10%–20% 余量，或实测。

## 2. 为什么是加，不是乘

原文结论里的三个数看起来像可以连乘的系数，其实分母不同：

| 原文说法 | 实际分母 | 能不能直接乘 |
| --- | --- | --- |
| Anytime 1024 约慢 1.9 倍 | Anytime 1024 / JavaE，同 prefix/LTR/暴力关闭 | 不能；只是算法对比，不是配置系数 |
| prefix 100→50 省约 40% | (100 的时间 − 50 的时间) / 100 的时间，整次调用 | 不能；已经包含 LTR 的变化 |
| LTR 15→10 省约 14% | (15 的 LTR − 10 的 LTR) / 15 的 LTR，只是 LTR 部分 | 不能；分母是 LTR 部分，不是整次调用 |

所以 `1.9 × 0.6 × 0.86` 这种算法没有意义：它把“算法对比”“整次调用”“LTR 单项”混在一起乘了。

**能相加的证据**：LTR 15→20，30×16 的 LTR 部分 +2.580 ms；Anytime 1024 的完整调用实测 +2.66 ms。差 0.08 ms；按整次调用算，三个棋盘（9×9、30×16、30×30）的加法估算误差依次为 +0.3%、−0.4%、−0.2%。这说明根层 LTR 的毫秒差几乎原样进入总时间。

**不能相加的地方**：

- **prefix 和 LTR 重叠**：prefix 同时影响 Semi 和 LTR；先改 prefix，LTR 那 14% 的分母已经变了。两个都改时，不要把两个百分比/毫秒差直接相加，除非你只想做很粗的一阶估计。
- **暴力是替换**：暴力触发时，用暴力耗时替换普通算法耗时，不是“普通算法 + 暴力”。所以 JavaE 表里的 +2.01 ms 不能直接搬到 Anytime 2000 上；Anytime 在残局本身更慢，替换后的增量会变小，甚至可能为负。
- **根概率不在表里**：所有时间都是根概率算好之后的部分；端到端要另加。

## 4. 基础算法：JavaE / Anytime N / LowRisk

基准：Templates、prefix 100、LTR 15、暴力关闭。平均每次猜测，单位 ms。

| 算法 / 节点预算 | 9×9 / 10 | 30×16 / 99 | 30×30 / 225 |
| --- | ---: | ---: | ---: |
| LowRisk | 0.0003 | 0.0006 | 0.0010 |
| JavaE | 2.212 | 9.027 | 20.136 |
| Anytime 0 | 2.208 | 9.053 | 19.975 |
| Anytime 256 | 2.867 | 11.044 | 24.087 |
| Anytime 512 | 3.591 | 13.062 | 27.965 |
| Anytime 1024 | 4.966 | 17.256 | 35.934 |
| Anytime 1280 | 5.599 | 19.411 | 40.229 |
| Anytime 2048 | 7.578 | 25.367 | 51.899 |
| Anytime 4096 | 13.224 | 41.333 | 82.553 |

- **JavaE**：直接查表。
- **Anytime N**：节点预算近似线性加价。用公式比逐行插值快：
  - 9×9：`t ≈ 2.19 + 0.00268 × N`
  - 30×16：`t ≈ 9.11 + 0.00789 × N`
  - 30×30：`t ≈ 20.26 + 0.01528 × N`
  - N 在 0–4096 内；N=2000 得 7.55 / 24.9 / 50.8 ms。
  - 公式是拟合值；要更贴表就在相邻两行间线性插值。N=2000 的插值是 7.45 / 25.0 / 51.2 ms，和公式差 <0.5 ms。
- **Anytime 0 基本就是 JavaE**：9×9 2.208 vs 2.212，30×16 9.053 vs 9.027，30×30 19.975 vs 20.136。可以把它当“不续搜的 JavaE”。
- **Anytime 1024 vs JavaE**：耗时比值为 2.24 / 1.91 / 1.78（9×9 / 30×16 / 30×30），绝对增量是 +2.754 / +8.229 / +15.798 ms。比值在 9×9 最大，但绝对增量在 30×30 最大；排时间预算看 ms，不要拿比值连乘。
- **LowRisk**：0.0003 / 0.0006 / 0.0010 ms，只是选格；根概率已经算好。它不适合和 JavaE/Anytime 放在同一张“吞吐量”表里比，因为大头在根概率。

JavaE 和 Anytime 1024 的 P99 / 最大值，单位 ms：

| 棋盘 | JavaE | Anytime 1024 |
| --- | ---: | ---: |
| 9×9 / 10 | 6.035 / 7.960 | 12.904 / 31.495 |
| 30×16 / 99 | 21.392 / 78.668 | 67.388 / 221.061 |
| 30×30 / 225 | 47.245 / 145.137 | 162.925 / 680.211 |

节点预算表使用相同盘面的配对测量，所以相邻两行的差值比绝对值更可靠。Anytime 2000 的 P99 未测；不要用平均值代替。

## 5. 模板前缀：相对 100 的毫秒差

基准：JavaE、LTR 15、暴力关闭。平均每次猜测，单位 ms。30×16 从 100 降到 50 是 9.027 → 5.408 ms，少 3.619 ms（约 40%）；9×9 少 0.499 ms，30×30 少 9.007 ms。

| 前缀 / 路线 | 9×9 / 10 | 30×16 / 99 | 30×30 / 225 |
| --- | ---: | ---: | ---: |
| 1 | 0.201 | 0.525 | 0.981 |
| 25 | 1.360 | 3.270 | 6.348 |
| 50 | 1.713 | 5.408 | 11.129 |
| 100 | 2.212 | 9.027 | 20.136 |
| 200 | 3.061 | 16.155 | 36.363 |
| OldJava | 0.192 | 0.482 | 0.920 |

以 100 为 0 的差值，单位 ms：

| prefix | 9×9 | 30×16 | 30×30 | 置信度 |
| ---: | ---: | ---: | ---: | --- |
| 1 | −2.011 | −8.502 | −19.155 | JavaE 实测 |
| 25 | −0.852 | −5.757 | −13.788 | JavaE 实测 |
| 50 | −0.499 | −3.619 | −9.007 | JavaE 实测 |
| 100 | 0 | 0 | 0 | 基准 |
| 200 | +0.849 | +7.128 | +16.227 | JavaE 实测 |

用法：`基础算法 + 上表差值`。例如 30×16 的 JavaE + prefix 50 ≈ 9.027 − 3.619 = 5.408 ms（就是原表值）。

注意：

- 这张表是 **JavaE** 的整次调用，已经包含 Semi 和 LTR 的变化。它不能直接证明 Anytime 下 prefix 的差值一样；Anytime 子节点还会做 Semi 检测，prefix 越大，子节点可能越慢。所以 **Anytime + prefix ≠ 100** 是低置信度，尤其是 prefix > 100，实际可能比“基础 + 差值”更慢。
- prefix 50 vs 100 的推荐格变化：0.1% / 0.5% / 0.6%；prefix 25：1.1% / 3.0% / 1.2%。时间省了不等于选点不变，最终要看胜率。
- OldJava 是另一条路线，不是 prefix 值：0.192 / 0.482 / 0.920 ms，比 JavaE 快很多。但它会**漏算一批 50-50**，搜索树上的选点不精确；它比 JavaE 快，有一部分就是少算这些换来的，不是同等精度下的加速。推荐格变化 3.2% / 10.2% / 18.8% 是这种漏算的表现，不是“风格不同”。追求强度时不要只看它的速度。
- Semi 的“跳过其他候选”是另一回事：它检测的是**无法避免的** 50-50，若存在则在实战发生的对局中最优，所以直接短路普通候选；数学上有反例，但概率可忽略。它和 OldJava 的“漏算一批 50-50”不是同一类问题。

## 6. LTR 事件上限：相对 15 的毫秒差

基准：prefix 100，单独计量 LTR 准备和 influence 查询；遇到 Forced / Semi 时按 0 计入。平均每次猜测，单位 ms。30×16 从 15 降到 10 是 8.596 → 7.374 ms，少 1.222 ms（约 14%）；调到 20 则 11.176 ms（+2.580 ms）。

| 事件上限 | 9×9 / 10 | 30×16 / 99 | 30×30 / 225 |
| --- | ---: | ---: | ---: |
| 5 | 1.268 | 6.762 | 15.270 |
| 10 | 1.555 | 7.374 | 16.576 |
| 15 | 2.045 | 8.596 | 19.205 |
| 20 | 2.749 | 11.176 | 24.265 |

以 15 为 0 的差值，单位 ms（只测到 20，20 以上不要外推）：

| eventLimit | 9×9 | 30×16 | 30×30 | 置信度 |
| ---: | ---: | ---: | ---: | --- |
| 5 | −0.777 | −1.834 | −3.935 | LTR 实测 |
| 10 | −0.490 | −1.222 | −2.629 | LTR 实测 |
| 15 | 0 | 0 | 0 | 基准 |
| 20 | +0.704 | +2.580 | +5.060 | LTR 实测 |

用法：`基础算法 + 上表差值`。在 prefix 100 下，这个加法有交叉验证：30×16 从 15 到 20，LTR +2.580 ms，Anytime 1024 完整调用 +2.66 ms；按整次调用算，三个棋盘（9×9、30×16、30×30）的加法估算误差依次为 +0.3% / −0.4% / −0.2%。

**重点：LTR 事件上限不是“多算一点就更准”的线性旋钮。** 内部要为每个互相必安组按方向事件构建**容斥树**；上限调大后，树的分支和组合数会**指数增长**。本文只测到 20，30×30 的 LTR 最大值已经到 384.5 ms；再往上不要按上表的毫秒差线性外推，可能从几十 ms 直接跳到秒级甚至更久。实战默认 15，想省时间用 10；再往上先挑几个代表盘面单点实测，别扫参数。

注意：

- 这是 **LTR 部分**，不是整次调用；加到整次调用时，其他部分不变才成立。
- 如果同时改 prefix，prefix 的差值已经包含 LTR 变化，再把这个差值加进去会重复计算。要么只改一个，要么实测。
- LTR 20 的 P99 / 最大值（按本节口径，为 LTR 部分）：7.458 / 7.585、30.412 / 139.625、86.004 / 384.518 ms。长尾比平均值涨得快。

## 7. 暴力阈值：替换修正，不是追加

基准：JavaE 为普通算法，暴力取最佳招、单线程；每格为平均 / P99，单位 ms。暴力耗时按同一局面的测量结果**替换**普通算法耗时。

| 暴力阈值 | 9×9 / 10 | 30×16 / 99 | 30×30 / 225 |
| --- | ---: | ---: | ---: |
| 0（关闭） | 2.212 / 6.035 | 9.027 / 21.392 | 20.136 / 47.245 |
| 1000 | 2.201 / 6.035 | 9.032 / 21.392 | 20.142 / 47.245 |
| 10000 | 2.369 / 6.044 | 11.033 / 37.479 | 20.890 / 49.269 |

**为什么不能直接加**：暴力只在“可行摆法数 < 阈值”的残局触发。触发时，这次猜测的时间变成暴力时间 `B`，不再算普通算法时间 `A_b`；没触发时仍是普通算法时间 `A_n`。所以：

```text
t_with_brute = (1 − f) × A_n + f × B
t_without    = (1 − f) × A_n + f × A_b
Δ            = f × (B − A_b)
```

其中 `f` 是触发比例，`B` 是暴力残局均值，`A_b` 是普通算法在同样残局上的均值。**A_b 是关键，而它随算法变**：JavaE 在残局上很快，Anytime 2000 通常会慢很多。

30×16 的拆解（阈值 10000）：

- 残局 7834 次 / 约 50000 次采样 → `f ≈ 15.7%`。
- 暴力残局均值 `B = 16.083 ms`。
- JavaE 表：9.027 → 11.033，`Δ_J = +2.006 ms`。
- 反推 JavaE 在残局上的均值：`A_b(J) = 16.083 − 2.006 / 0.1567 ≈ 3.28 ms`。
- Anytime 2000 基础 25.0 ms；先按比例假设 `A_b(A) ≈ 3.28 × 25.0 / 9.027 ≈ 9.08 ms`，范围见下表。
- `Δ_A ≈ 0.1567 × (16.083 − 9.08) ≈ +1.10 ms`。

三个棋盘的估算：

| 棋盘 | f（约） | B（ms） | JavaE Δ（实测） | Anytime 2000 Δ（估算） | 估算范围 |
| --- | ---: | ---: | ---: | ---: | --- |
| 9×9 / 10 | 7.1% | 2.122 | +0.157 | ≈0 | −0.2～+0.2 |
| 30×16 / 99 | 15.7% | 16.083 | +2.006 | +1.1 | −0.5～+2.0 |
| 30×30 / 225 | 3.0% | 31.134 | +0.754 | +0.5 | −0.2～+0.8 |

`f` 来自约 50000 次采样的残局表；上面的设置表只用其中前 10000 次猜测，两者样本范围不同，`f` 是近似值。范围的下限来自“Anytime 在残局上比暴力还慢”（A_b 接近或超过 B），上限来自“Anytime 在残局上和 JavaE 差不多快”（A_b 接近 JavaE）。真实值取决于残局有多小；没有实测就只能给范围。

**阈值 1000**：0 / 1000 / 10000 的平均分别是 9.027 / 9.032 / 11.033（30×16）。1000 和关闭几乎一样（+0.005 ms），因为触发比例很小。想省时间又不想放弃太多残局强度，先用 1000；10000 是拿长尾换精确度。

单独看“布局数 < 10000、实际运行暴力”的残局：

| 棋盘 | 残局次数 | 平均 ms | P99 ms | P99.9 ms | 最慢一次 | 最慢 1% 消耗的总时间比例 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 9×9 / 10 | 3571 | 2.122 | 19.641 | 164.811 | 2.85 秒 | 77.3% |
| 30×16 / 99 | 7834 | 16.083 | 370.904 | 2067.703 | 4.27 秒 | 58.1% |
| 30×30 / 225 | 1514 | 31.134 | 580.393 | 1865.293 | 1.89 秒 | 31.9% |

30×16 超过 1 秒的有 19 / 7834（约 0.24%）；最慢 4.27 秒。10000 的 P99 从 21.392 升到 37.479 ms，最大值会到几秒。**平均值只涨 2 ms，不代表交互不会卡 4 秒。**

暴力的其他参数（30×16 残局，单位 ms）：

| 暴力设置 | 平均 | 最慢一次 |
| --- | ---: | ---: |
| 最佳招 / 单线程 | 16.08 | 4.27 秒 |
| 全部候选 / 单线程 | 28.40 | — |
| 最佳招 / 2 线程 | 11.13 | 2.55 秒 |
| 最佳招 / 5 线程 | 7.92 | 1.65 秒 |

多线程主要压长尾；对整次均值的影响按 `f` 缩放，30×16 大约 1 ms 量级。全部候选（单线程）会明显增加 `B`，估的时候把 `B` 换成 28.40 再套公式；多线程全部候选没有现成数据。

## 8. 其他设置和本机参考

- Anytime 1024 的搜索宽度在 `6/3/1`、`3/3/1`、`6/2/1`、`6/3/2` 间变化时，三个棋盘的平均耗时变化约在 **2% 以内**；推荐格也会变化。估的时候按 0 处理，默认 `6/3/1`。
- 在根概率 + JavaE 的对照中，30×16 的 Auto 和 AutoSA 分别为 **9.101、9.102 ms**；另外两个棋盘的平均值也很接近。按 0 处理。
- 本机 Ryzen 7 9850X3D 的第一轮测量中，JavaE / Anytime 1024 平均每次猜测：9×9 为 **0.917 / 1.974 ms**，30×16 为 **3.178 / 6.549 ms**，30×30 为 **7.025 / 12.886 ms**。这轮各棋盘分别使用 2407、3297、1680 个配对样本。这是另一台机器，不能把绝对值直接套到服务器上；只看量级和比例。

## 9. 估算误差与不能估的东西

- **不含根概率**：所有时间都是根概率算好之后的部分。真实端到端要加根概率，本文没有系统测。
- **跨设置组合是低置信度**：Anytime + prefix ≠ 100、同时改 prefix 和 LTR、Anytime + 暴力 + 多线程/全部候选，这三类都留 10%–20% 余量，或实测。
- **LTR 上限 >20**：本文只测到 20；内部容斥树可能指数增长，不能按上表线性外推，必须实测。
- **P99 / 最大值**：只有 JavaE 和 Anytime 1024 有完整 P99；Anytime 2000 未测。平均值不能代替长尾；30×16 单线程暴力 10k 可能到几秒，5 线程最长约 1.65 秒。
- **单机单版本**：服务器、编译器、代码版本不同，绝对值会变；本文适合做相对规划和量级判断。
- **未测胜率**：时间省了不代表选点/胜率不变；prefix 和 LTR 的推荐格变化需要结合胜率决定。
- **OldJava 不是免费加速**：它更快，但会漏算一批 50-50，搜索树上的选点不精确；强度敏感时不要拿它的速度当默认选择。
- **首次调用与缓存**：第一次普通评分会触发 LTR 表编译，prefix 100 约 0.46–0.56 秒，prefix 200 约 2.4 秒；这些从稳态和长尾统计中剔除。测试调用不使用建议缓存，实际程序如果复用缓存，可能更快。

## 10. 原始测量与测试方式

服务器为 Intel Xeon Platinum、8 逻辑 CPU，GCC 12.3 `-O3`；代码版本 `7871ded`。用 JavaE、prefix 100、LTR 15、暴力 1000 串行进行完整对局，分别玩了 **72387、15639、9054 局**，每种棋盘收集约 **50000 次**需要猜测的局面。

| 棋盘 | 完整对局 | 采样猜测 | 普通设置计时猜测 | 不同盘面 | 暴力残局 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 9×9 / 10 | 72387 | 约 50000 | 约 10000 | 1921 | 3571 |
| 30×16 / 99 | 15639 | 约 50000 | 约 10000 | 6913 | 7834 |
| 30×30 / 225 | 9054 | 约 50000 | 约 10000 | 7520 | 1514 |

将实战局面打乱后，各普通设置对同一批约 10000 次猜测逐一计时；重复盘面按实战出现次数保留。暴力另扫描约 50000 次采样中符合条件的残局。根概率预先算好，测试调用不使用建议缓存；模板表预热后复用。以上是实战采样局面的对照，不同设置的完整对局尚未分别运行。

## 11. 术语速查

| 词 | 含义 |
| --- | --- |
| JavaE / JavaEval | 普通评分算法；本文基准算法 |
| Anytime N | 在 JavaE 评分上继续搜索；N 是每步节点预算 |
| LowRisk | 只按安全率选格；根概率已算好时极快 |
| Templates | 50-50 模板路线；同时包含 Semi 和 LTR |
| OldJava | 旧 50-50 路线；更快，但会漏算一批 50-50，搜索树选点不精确 |
| Semi | 模板检测到的**无法避免的** 50-50 局面；若存在，则在实战发生的对局中最优（数学上有反例，但概率可忽略），因此跳过普通候选 |
| LTR | 长期风险；由模板前缀和事件上限控制成本 |
| 模板前缀 | Semi / LTR 共用前 N 个模板；越大越慢、覆盖越多 |
| LTR 事件上限 | 每个互相必安组按方向事件概率取前 N 项；内部算容斥树，N 调大可能指数爆炸 |
| 暴力阈值 | 可行摆法数小于该值时改用精确暴力；0 关闭 |
| P99 / P99.9 | 99% / 99.9% 的测量不超过该值 |
| 配对测量 | 同一批盘面逐一对不同设置计时，减少盘面差异 |
