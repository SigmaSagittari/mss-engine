# 编码与审查 Prompt

范围：适用于 `code/`。

前置：范围、优先级、必读清单和授权见 `AGENTS.md`（`../../AGENTS.md`）；规则归属见 `docs/README.md`（`../README.md`）。

本文件管什么：怎么动手、怎么判断、怎么报告。范围与授权类规则不在这里。

## 修改前

### 看现场

- 检查工作树、分支和本次 diff。
- 不覆盖、不重置、不混入无关文件。

### 守住范围

- 只处理用户要求的范围，以及由此必需的改动。
- 用户只要求审查时，只审查本次 diff 或指定范围。
- 查看未改动的代码，只为确认依赖、定义和调用。

### 不造结构

- 不添加胶水层、重复规则、镜像状态、额外 facade，也不加只转发参数的包装。
- 现有 API 确实无法完成任务时，说明三件事——缺少的 API、调用者、最小职责——先取得批准。

### 不扩目标

- 不主动设计"更好的架构"，也不把目标扩成重构。
- 用户要求架构方案时，按 `AGENTS.md` 的授权规则处理。

## 仅审查

- 每条意见给出四样：文件与行、可复现条件、实际影响、最小修复方向。
- 区分"源码已证实的事实"和"推断"。没有证据就继续查，不要停在推断上。
- 报告用中文，按严重程度排序。
- 没有可证实的问题时，明确写「未发现可证实的问题」，并列出检查范围和未执行的验证。

## 可靠性判断

### 先信任，再追查

- 信任已经测过的组件。
- 遇到意外、矛盾或奇怪的结果，先追查，按 Bug 处理。

### 不要"更稳健"的假动作

禁止为了"更稳健"而做下面任意一件事：

- 重复验证 API 已经保证的条件；
- 添加兜底结果；
- 吞掉错误；
- 静默回退；
- 继续在无效状态上运行。

### 错误不许化妆

- 不得返回默认值、空结果或其他假成功结果。
- 不得把内部致命错误伪装成业务返回。
- `assert_`、`warn_` 和禁止的终止方式，按 `implementation.md`。

### 性能也是正确性

- 性能回退也是 Bug。
- 用实际输入和完整调用路径定位性能问题。

### 什么时候要写注释

- 确认不是 Bug 时，在相关代码处用中文注释说明依据。
- 必须读函数实现才能解释本次行为时，也留最小必要的中文说明。

## 风格与审查方法

### 贴合现有代码

- 严格贴合相邻实现的命名、格式、文件边界和已有 API。

### 重构时的态度

这个项目所有代码都是你写的。所以：

- 重构时不要刻意遵循旧实现，也不要刻意修改——尤其当旧实现与风格冲突时。
- 默认不增加无关行。
- 新增的行数必须由功能需要证明。
- 即便新增功能，也应当尽可能精简。

### 分工

- C++ diff 按 `style.md` 检查。
- 可靠性、性能与领域职责按 `implementation.md` 检查。

### 怎么查证

- 审查每个疑点时，追到类型定义、函数定义、调用点及关联状态。
- 职责边界按 API 的定义模块判断。

## 工具与回复

### 执行

- 构建、测试和 benchmark 按 `operations.md` 执行。

### 语言

- 用中文回答。
- 数学内容使用 LaTeX，不放进代码块。
- 用直白、具体的中文，少用套话、空泛评价和模型常见的填充词。

### 给数据

- 用户只要数据时，用表格给出实际取得的数据。
- 只有严重妨碍阅读时才压缩表格/数据。

### 说清楚

- 直接说明要做或已做的动作及证据。
- 说明取舍时只写会影响决策的方面，省去已知的平衡句。
- 报告三件事：改了什么、为什么、验证了什么。
- 只说实际执行过的验证。

## 未完成工作

- 每次回复前，核对用户的要求是否全部完成。
- 若还有跨轮未完成的明确目标，创建或更新长期 goal，并继续推进。
- 用户明确暂停时才暂停。
- 需要用户手动执行安全操作才能继续时（例如结束阻塞进程），直接说明具体操作和阻塞影响。
