# 测试 Prompt（mss0.16）

本文件只适用于 `mss0.16`。必读清单见 [AGENTS.md](../../AGENTS.md)，规则归属见 [docs/README.md](../README.md)。mss1.5（Git 标签 `v1.5-archive`） 的测试树和旧测试 API 都已废弃，不要照搬。

测试树尚未落地时，新增测试前先向用户确认入口、目录和构建方式；不要自行复制 1.5 的 harness、注册器或夹具框架。

## 盘面来源与正确性判定

- 测试盘面优先来自固定种子的随机对局、真实运行记录或已发现的失败样本，尽量不要由测试作者手工构造。用户提供或明确要求的构造盘面可以直接保留；需要固定回归时，优先固化这些来源的盘面与操作序列。
- 正确性测试应围绕 API 契约和实际结果设计，优先采用生成式差分或性质检验：从实际生成的盘面、候选集合和操作结果，按契约系统地派生后续合法输入及调用序列，再核对结果。不能把覆盖范围寄托于“写测试时有没有想起这个特例”，也不能靠不断追加手工特例代替检验方法。
- 判定依据必须有独立来源，例如小规模完整枚举、可信参考实现或可证明的不变量；核对契约相关的完整语义结果及状态变化，不能只看是否崩溃、少量统计量是否相同或最终是否获胜。预期值不能照抄被测实现；优化前后比较可验证行为是否改变，但不能单独证明原实现正确。
- 失败时保留生成种子、盘面、操作序列及预期与实际结果的差异，使失败可以重放并固化为回归；不要求靠人工枚举所有情况，也不把有限测试通过当成不存在遗漏的证明。

## 随机多局测试

- 对局数上限与目标时长都是有限的正数；测试驱动两者都受约束，先达到任一限制就停止。禁止用 0、负数或魔法值表达“无限”或关闭限制。
- 若用例的目标是完成 `maxGames` 局，必须确认实际完成数等于目标；时限先到就报告用例未完成，不把部分数据当作成功。
- 若用例的目标是测固定时长吞吐，`seconds` 是测量目标，`maxGames` 是保护上限；游戏数先到时说明测量被上限截断，不能把它报告成完整的定时吞吐结果。
- 固定随机种子，确保相同测试设置可复现；输出测试名、盘面尺寸和雷数、种子、目标时长、目标对局数、实际对局数、胜负、实际耗时及本用例需要的统计。
- 进程内的合作式时间检查不是硬超时；一局可能使实际耗时超过目标时长。外部硬超时按 [operations.md](operations.md) 设置。
- 摘要对象保存实际测得的统计，不复制配置目标冒充测量结果。百分比、均值和吞吐量必须先确认分母非零由测试前置条件保证；不要用默认值掩盖没有采样的情况。

## 固定盘面和引擎回归

- 固定盘面、种子、预期布局数、预期胜局数、操作顺序和断言在对应测试用例内集中定义。不要把某个残局或断言塞入公共 helper。
- 对概率增量 API 的专门回归，可以直接调用被测模块并检查合法候选数、状态一致性或用户指定的不变量；这类测试不必伪装成随机对局。
- 对 BruteForce 单线程/多线程比较，应从当前公开 API 设置求解选项，并检查同一固定盘面上的明确结果。不要用测试自创枚举代替生产 API，也不要让这组引擎选项变成其他测试的公共配置。
- 需要 Game 行为时，先读 `GameControl::Game` 的实际声明，使用现有 API；缺少所需行为时明确报告 API 缺口，不在测试里默默复制第二套完整玩法。
- 保持测试自身关注点：固定概率盘面验证概率/增量接口，固定残局验证枚举和结果，随机对局统计实战行为。别在一个用例里混进不相关的初始化、性能指标或规则实现。

## 测试自己的配置

- 测试运行设置、测试目标和测试上限属于测试层。使用测试自己的配置类型（例如 `test::Config` 或用户明确指定的测试层类型），不能把生产 `mss::Config` 当作测试配置，也不能删除测试配置、把它替换成生产配置。
- 在需要统一随机完整对局参数时，测试配置集中保存盘面行数、列数、雷数、目标时长、最大对局数，以及确实被多个这类用例共同使用的测试模式。每个用例只构造一个配置值；不要在各用例散放同一组 `kRows`、`kCols`、`kMines`、`kDurationSeconds`，也不要把同一设置拆成一串位置参数。
- 生产引擎的 `mss::Config` 和测试配置是不同职责。测试运行设置、测试目标与测试上限由测试配置持有。只有当被测生产 API 的真实签名要求生产配置时，测试才按该 API 的需要提供它；这不使 `mss::Config` 成为公共测试配置，也不授权把它加入通用测试驱动参数。
- 具体引擎参数只放在确实测试该参数的用例设置中；不要把生产 `Config` 的所有字段复制到测试配置，也不要让某个测试的临时选项污染所有测试。
- `BruteForce::Config` 和 `BruteForce::Workspace` 属于 `BruteForce` 模块，不是测试层配置；按生产 API 分别传给 `BruteForce::solve`。它们不互相嵌套，也不把引擎设置提升为所有测试的共享配置。

## 用例入口与文件

- 新用例沿用用户指定的测试入口和相邻文件风格；不新增第二套入口、命令行注册器、插件表或生产入口开关，除非用户明确要求。
- 公共文件只放多个测试确实共用的类型和驱动。用例数据、局部 lambda、期望值和只被一个用例调用的步骤留在该用例。
- 不能为了“统一架构”擅自把本来以头文件组织的测试拆成 `.cpp`，或创建胶水层、fixture 框架和通用注册系统；这些都是跨文件架构更改，必须按总 Prompt 取得授权。
- 测试的名字、seed、输入、断言和输出应当能让失败复现；不输出无法说明来源的汇总数字。

## 运行

- 实现、修复或测试任务中，correctness 测试可以直接运行；报告实际命令、耗时、退出状态和用例输出。任何运行都设外部硬超时，防止死循环或失控占用机器。
- benchmark 按 [operations.md](operations.md) 执行。
